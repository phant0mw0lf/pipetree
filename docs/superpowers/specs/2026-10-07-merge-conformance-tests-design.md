# Merge-strategy conformance tests - design

## Intent (what the user said)
"I also want a test that all merge types like scd1, scd2 and so on are working 100% correct. I don't want to ship any rubbish." Decision (user): run it **both** as part of pipetree's own test suite (local Spark + Delta) **and** as a job on Databricks (real runtime; later Fabric Spark 4.1).

Success = for every strategy and every merge option, over many multi-batch histories, the table pipetree produces equals what an independent reference model says it must be, after every batch; every divergence is either a pipetree bug (fixed) or a documented decision (the model is changed deliberately). Not "more examples": a model plus generated histories, so the combinations nobody thought of are exercised.

## The semantics under test (source: blog part 1 + merge.py; the model is written from these rules, not from the code)
- **replace**: table = the source batch, every run. **append**: table = old rows + batch rows (a retry of the same `_execution_id` first deletes that run's rows).
- **scd1** (key = `business_key`, composite allowed): new key -> insert; existing key with a changed tracked column -> update in place (`_updated_at`, `_execution_id` move, `_inserted_at` stays); unchanged -> untouched (`_updated_at` unchanged); a batch with several rows per key is reduced to one (`sequence_by` list decides, with ties broken deterministically) and the dropped count reported.
- **scd2**: new key -> insert current version; changed tracked column -> close the current version (`_valid_to`, `_is_current = false`) and open a new one; unchanged -> untouched; exactly one current version per live key; versions of a key never overlap and have no gaps.
- **delete_when** marks a source row as a delete; **delete_mode**: `soft` (row stays, `_is_deleted = true`; scd2 closes the current version and opens none), `hard` (scd1 only: row removed; scd2 + hard is rejected by the loader), `ignore` (the delete signal is dropped).
- **ignore_columns**: excluded from change detection.
- **init**: full reload = table rebuilt from the batch (fresh version-1 history), whatever existed.
- **unknown_member** (+ **surrogate_key**): one extra row with the typed sentinel key (-1 numeric, NULL string, 1900-01-01 date), seeded once, never versioned or touched by later merges; surrogate keys are generated by the table, stable per row, never emitted by the source.
- **schema_policy** (`evolve` / `fail` / `ignore`) as documented in the README.

## Decisions (user, 2026-10-07; also in memory `pipetree-merge-semantics-decisions`)
1. **scd1 soft delete, key returns with identical values:** the row becomes active again (`_is_deleted = false`, `_updated_at`/`_execution_id` move). Today it stays deleted (bug to fix).
2. **scd2, deleted key returns:** a NEW current version opens; the closed version stays closed.
3. **Late/older `sequence_by` in a later batch:** last batch wins; `sequence_by` only breaks ties within a batch (today's behaviour).
4. **NULL business key without `unknown_member`:** single-column key with NULL -> dropped with a WARNING and a note; composite key -> a NULL in one component is a legitimate value (null-safe match, no pile-up on reruns), a row is dropped only when the WHOLE key is NULL. `unknown_member` tables keep dropping a row with a NULL in ANY key column (the NULL is the unknown member's string key). Today NULL-key rows are re-inserted every run (observed on Databricks).
5. **`delete_mode: ignore`:** delete rows are removed from the batch BEFORE deduplication, as if they never existed (a key with only a delete row is not inserted).
6. **Delete row for a key not in the table:** no-op (soft and hard).
7. **scd1 hard delete, key returns:** fresh insert (new `_inserted_at`, new surrogate key).
8. **`ignore_columns` changing alone:** the current row is updated in place (scd1 and scd2); no new scd2 version; `_updated_at`/`_execution_id` are NOT bumped.

Each decision becomes a rule in the model with a `# decision N` comment; code that differs is a bug the model finds. Also found while observing the edge-case job: with `schema_policy: ignore` the schema note says `schema: added: extra (string)` although the column is not written - the note wording must say it was ignored (fix in the same pipetree work).

## Design
- **Reference model** - `pipetree.testing.merge_model` (pure Python, no Spark import): `apply_batch(state, batch, table_config, execution_id) -> state` for all four strategies and all options above. Small on purpose (one screen per strategy) so it can be reviewed by reading it against the rules above.
- **Generator** - seeded `random` (no new dependency; reproducible by seed; usable on a cluster): a random but valid table config (strategy x delete_mode x sequence_by shape x ignore_columns x composite key x unknown_member/surrogate_key; schema policy as a separate dimension) plus a history of 2-6 batches over a tiny key space (3-8 keys, 0-8 rows per batch) built to hit the interesting cases: several rows per key in a batch with equal and different sequence values, deletes, resurrection, out-of-order sequence values, empty batches, batches repeated verbatim (idempotence), NULL in non-key columns, NULL keys, column added/dropped, a final `init`.
- **Harness** - `pipetree.testing.merge_harness`: runs the same history through the real `merge_*` functions (or through `SparkAdapter.run_table`) on a given `spark`, and after every batch reads the table, normalises it (drop audit timestamps; keep `_is_deleted`, scd2 `_is_current`, version order, which batch inserted/updated each row via `_execution_id`) and compares it with the model. Returns a list of divergences with the **seed, config and batch history** that reproduces them (a failing case is a one-line repro).
- **Invariants checked independently of the model** (so a model bug cannot hide a table bug): scd2 one current row per live key, no overlaps/gaps, closed versions immutable across later batches; scd1 `_inserted_at` never changes; the unknown member is never duplicated or changed; running the same batch twice is a no-op (scd1/scd2/replace); `init` equals a fresh build of the last batch.
- **Where it runs**: (a) pipetree `tests/merge_conformance/`: a fixed corpus of regression histories (every divergence ever found, committed with its decision) plus N random seeds per strategy (N small in CI, larger on demand: `PIPETREE_CONFORMANCE_SEEDS=2000`); (b) scale-bench job `pipetree_merge_conformance` (single-node cluster, one notebook task per strategy so each is visible in the job graph; same seeds; results in a Delta table like the edge-case job) so DBR's Delta - and later Fabric's Spark 4.1 - are checked with the same histories.
- **Package surface**: `pipetree.testing` is test tooling, documented as such (not a stable API), no new runtime dependency.

## Out of scope (v1)
Kusto/SQL sources, concurrency (two runs writing one table), performance, very large batches, `append` retries across crashes beyond the `delete_by_execution_id` contract.

## Deliverables and order
1. Decisions 1-8 answered by the user. 2. Model + generator + harness + invariants, unit-tested (the model against hand-written examples that restate the blog's rules). 3. First run on local Spark: **every divergence is reported as a finding** (not fixed silently); user decides model-vs-code per finding. 4. pipetree PR(s): the tests plus the agreed fixes. 5. scale-bench PR: the Databricks job. 6. Run on dev, report.
